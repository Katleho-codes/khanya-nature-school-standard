# DECISIONS.md

Architecture, content and scope decisions for the Khanya Nature School demo. The goal was a convincing sales demonstration that is also a real working CMS, not a static mock-up.

## Platform and repository

### pnpm workspace with two apps

`web/` and `api/` are separate packages. The public site needs a server-rendered front end, and the CMS needs a real API with its own auth, validation, file uploads and database access. Keeping them separate makes the API boundary explicit and lets each app build and run on its own.

Consequence: two dev servers, two environment files, and a rewrite from `/api/*` to the API. The benefit is that the CMS is not a collection of server actions pretending to be an API.

### Next.js App Router on port 3002

The public site uses server components and server-side data fetching. This keeps the first paint complete, keeps SEO metadata and JSON-LD on the server, and avoids shipping a large client data layer for a content site.

The admin is mostly client components because it is an interactive CRUD interface. Admin pages sit under a protected route group with a server-side session check, then use `adminFetch` for mutations.

### Express 5 and Prisma 7 on port 4002

Express remains a small, understandable API layer. Prisma provides typed queries, migrations and seed support. Prisma 7 is used with `prisma.config.ts` and `@prisma/adapter-pg` because that is the current configuration model.

The generated Prisma client is emitted as ESM into `api/src/generated/prisma` with `importFileExtension = "js"`. It is ignored by git and regenerated by `postinstall` or `prisma generate`.

Consequence: a clean clone must run `pnpm install` before typecheck or build, otherwise the generated client is absent.

### PostgreSQL 16 in Docker

`docker-compose.yml` pins `postgres:16-alpine`, maps host port 5442 to 5432 and uses a named volume. A clean clone can start the database with one command and get the expected version.

### Local PostgreSQL fallback

Docker Desktop was not available on the build machine. Development used a dedicated local PostgreSQL 18 cluster at port 5442 with the same database, user and password. The schema, Prisma version and container definition still target PostgreSQL 16, and nothing in the application depends on an 18-only feature.

Consequence: `pnpm dev` cannot be the only documented start path. The README documents the local fallback, and the API and web app can be started separately.

### TypeScript and ESLint pins

TypeScript is pinned to 5.9.3 because typescript-eslint 8.x does not support TypeScript 7 yet. ESLint is pinned to 9.39.5 because the Next.js ESLint plugins do not support ESLint 10 yet. pnpm is configured with `allowBuilds` for native packages and `minimumReleaseAge: 0` so the locked versions install reliably.

## Data and content

### API is the source of truth

Public routes fetch branches, programmes, posts, events, albums, documents and settings from the API. Hard-coded copy is limited to editorial sections that are not presented as CMS-managed, plus interface labels and the privacy notice.

Consequence: the web app cannot show content that is not in the database. A failed API call should fail visibly rather than silently falling back to invented content.

### Public fetches use `cache: "no-store"`

An admin edit must be visible on the next public page load. For a small school site, the consistency benefit is worth more than static caching. The data sets are tiny.

Consequence: public pages are rendered on demand. A production version could add tag-based revalidation later, but that would need a publish or invalidation workflow that is out of scope here.

### Branch activation is a first-class rule

A branch has one `isActive` flag. Deactivating it must remove it from the header, footer, branch list, public branch route, navigation API, enquiry branch picker, contact page and sitemap. Programme links on that branch also stop being offered.

The implementation enforces this in the public queries rather than hiding links in the front end. The Playwright admin suite checks the header, footer and sitemap propagation.

### Seeded dates are relative to run time

News and events are seeded relative to the seed date so the demo always has recent posts and upcoming events. This matters for a sales demo that may be opened months after the build.

Consequence: screenshots are not reproducible unless the database is reseeded at the same time. That trade-off is preferable to a demo that looks stale.

### Seed runs through better-auth

Demo users are created through a seed-only better-auth instance with sign-up enabled. Password hashes therefore match the sign-in path, and the normal application keeps public sign-up disabled.

`pnpm db:seed` is destructive. It clears content and users, writes a complete demo school and regenerates the seed PDFs. It is the supported way to return to a clean demo state.

### Markdown is trusted CMS content

Article and page body copy is Markdown. It is rendered with `marked` without sanitising because only signed-in staff can write it. Public user input never reaches the Markdown renderer.

Consequence: if a future version allows untrusted authors, the renderer needs sanitisation or a strict allow-list.

### Media is local to the demo

Uploads use multer memory storage and are written to `api/uploads/`. File type is detected from magic bytes, images are measured with `image-size`, the limit is 8 MB, and only JPG, PNG, WebP and PDF are accepted. Images require meaningful alt text.

Local disk is appropriate for a demo and keeps setup small. A production deployment must move uploads to object storage and add malware scanning and retention rules.

### Seeded image files are intentionally absent

The seed creates media records pointing at `/images/...` files that are not checked in. `Photo` and `PhotoFrame` fall back to branded placeholders with the correct aspect ratio. This keeps the demo presentable while leaving the photograph brief honest.

`web/public/images/README.md` lists every expected filename, ratio, minimum size and subject. There are 24 core images and 46 gallery images.

### Seed PDFs are generated

The seed uses `pdf-lib` to create six small PDFs in `api/uploads/`, covering the admission form, fee schedule, medical and dietary form, parent handbook summary, school calendar and what to bring. This makes document downloads real without checking binary files into git.

## Auth, roles and security

### better-auth instead of a custom auth system

better-auth handles email and password sign-in, sessions, cookie signing and Prisma-backed users. It is mounted directly in Express at `/api/auth/*`, and the web app proxies `/api/*` so browser cookies stay same-origin.

Public sign-up is disabled. Admin and editor roles are implemented with better-auth's admin plugin and access control. `isActive` is an application field kept in sync with better-auth's `banned` flag.

### Two roles, enforced in the API

Editors manage content, media, documents, enquiries and the outbox. Admins also manage users and site settings. Route middleware enforces the role. Hiding navigation items is not treated as security.

Branch-scoped permissions were deliberately not added. They would add a permission matrix, UI complexity and test cases that this sales demo does not need.

### Secure session defaults

Session cookies are httpOnly, sameSite `lax`, and secure when `SESSION_COOKIE_SECURE` is true. `BETTER_AUTH_SECRET` must be replaced before any real deployment. The default in `.env.example` is intentionally a demo value.

### Validation at the boundary

Request bodies and query strings are validated with Zod in the API. Public forms also validate in the browser for fast feedback. The API is still the authority.

### Rate limiting and form abuse checks

The public enquiry endpoint is rate limited. The form includes a honeypot field and a minimum fill time. These are lightweight deterrents appropriate to a small school site, not a full bot-management system.

## Design and accessibility

### Crayon and paper cut-outs, sunrise

The first visual direction used warm oat, forest green and ochre, with a Fraunces serif, italic accent words, letter-spaced small-cap labels, hairline rules, arched portraits and thin leaf line art. It read as a boutique magazine rather than a preschool. The owner asked for the warmth and play of the sibling Marula Kids demo without copying it.

The replacement identity is "Crayon and paper cut-outs, sunrise". Khanya means light, so the primary mark is a hand-drawn sun. The page is warm paper, the shapes are flat coloured paper with no ink outlines, the corners are irregular, the shadows are flat 3 px paper edges and the decorations are crayon scribbles. Baloo 2 carries headings, Mulish carries body and interface text, and Gaegu is limited to tiny handwritten annotations. The palette is paper, ink, sun, poppy, sky and meadow, each with one deep and one tint step.

This is deliberately different from Marula Kids. Marula uses ink-outlined stickers with hard offset shadows and a terracotta, yellow and leaf palette. Khanya uses unoutlined paper shapes, softer wobbly edges and a bright primary crayon palette.

Programme and branch colours are fixed so the same entity looks the same everywhere, including calendar dots and admin badges. Little Explorers is sun, Forest Kindy meadow, Bush School sky, Grade R Pathfinders poppy and Holiday Programme sun. Randburg is poppy and Fourways is sky. Only ink text sits on sun, sky and meadow. White text is used only on poppy-deep.

The old tokens, fonts, leaf motifs, arches, numbered labels, small-caps eyebrows, hairline rules and editorial prose class were removed rather than hidden. All colour still lives in theme tokens in `web/src/app/globals.css`. Components use token classes only.

### Light mode only

The brief asked for light mode only. Adding a dark theme would have doubled the colour and contrast checks for no sales benefit.

### Mobile first

Layouts start at small widths and expand. The header uses a desktop navigation at large widths and a full-screen mobile menu below it. Tables in the admin scroll inside their own containers rather than forcing the page sideways.

### WCAG AA and reduced motion

The site targets WCAG AA. Focus states are visible, the skip link is the first keyboard stop, images have alt text through the CMS, and axe scans cover public pages plus admin login and dashboard. Footer and admin text on dark green were increased in opacity after axe found contrast failures.

Motion is restrained and respects `prefers-reduced-motion`. There are no autoplay videos or unnecessary animations.

### WhatsApp is secondary, not a replacement for content

WhatsApp links are prefilled and context-aware. The floating button appears on small screens; desktop users get the header link and page-level buttons. The number comes from `NEXT_PUBLIC_WHATSAPP_NUMBER` as the fallback, and branch numbers come from CMS records.

## SEO

### One metadata helper

`pageMetadata` builds titles, descriptions, canonicals, Open Graph and Twitter metadata from page data and site settings. Dynamic pages use the CMS SEO fields when present and fall back to page copy. Admin forms show character counters and a search preview.

### Structured data where it earns its place

The home page emits `Preschool`. Articles emit `Article` and `BreadcrumbList`. Events emit `Event`. There is no attempt to mark up every page type.

### Sitemap reflects active content

The sitemap is generated at request time from active branches, published programmes, posts, events, albums and static routes. Inactive or unpublished content does not appear. `robots.txt` disallows `/admin` and `/api`.

## Testing

### Playwright with one worker

The smoke suite mutates real demo records, so it runs serially. Parallel workers would create flaky ordering and shared state problems for branch activation, enquiries and media.

### API and UI coverage

An API check script exercised the admin CRUD surface during development. The committed Playwright suite focuses on the journeys a buyer or editor will actually try: public routes, metadata, login, news CRUD, branch propagation, enquiry handling, media upload, editor restrictions, mobile layout and accessibility.

### Axe for accessibility

`@axe-core/playwright` runs WCAG A and AA rules on representative public pages, admin login and the dashboard. Axe is not a substitute for manual testing, but it catches the contrast and labelling regressions that are easy to introduce in a design-heavy build.

## Scope and intentional cuts

Out of scope: WordPress, payments, a parent portal, bookings, a newsletter, analytics, custom workflows, more than two roles, branch-scoped permissions, third-party integrations, a second language, dark mode, comments and site-wide search.

The demo also does not send real email. All messages go to the admin outbox for inspection. That keeps the demo self-contained and avoids accidental mail to fictional or real addresses.

## Known limitations

- Docker is unavailable on the build machine; the local database is PostgreSQL 18 rather than the specified 16 container. The application does not rely on the difference.
- Uploads use local disk and are not backed up or shared between instances.
- The outbox is a demo mail sink, not an email delivery system.
- There is no audit log beyond enquiry notes and timestamps.
- There is no publish scheduling, revision history or content approval workflow.
- There is no branch-scoped role model.
- The image files in the brief are not included. Placeholders are intentional until the school supplies photographs.
- The Playwright suite leaves enquiry and outbox records behind. Reseed before a clean handover.
